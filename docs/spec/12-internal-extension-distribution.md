# Internal Extension Distribution Baseline

Date: 2026-11-18
Status: Implementation baseline

原型工作台 (formerly GameFlow, current extension ID `codetypess.vscode-gameflow`) packaging uses standard VSIX. Package publisher/name come from the source manifest and must not be overridden using an older local installation. Display-name changes preserve identity; a publisher change creates a different extension ID and requires installation of that identity. Command IDs, configuration keys and document formats remain stable. Each extension embeds a shared self-update client and reads `<package.name>/metadata.json` from the distribution server; users install one VSIX. The standalone internal updater is legacy and is not required. Document IO and current editing remain available during update installation.

The initial origin is the provisional intranet HTTP endpoint `http://vsix.bitserver.wang`. Each extension reads its own `<package.name>/metadata.json`; the sibling `<version>.vsix` is the download target. Plain JSON metadata is Ed25519 signed; the client pins the public key and verifies package SHA-256 and manifest identity before installation. Signing keys never enter the public site or Git. Workspaces cannot override the update source or the user's automatic-check preference. Later HTTPS deployment must retain signature checks.

Release files are immutable. Upload and identity verification finish before per-plugin metadata is atomically replaced under a shared publication lock. Signed revisions increase across publications. Rollbacks require an explicit user action; ordinary polling only offers newer compatible stable versions.

Same-name metadata directories reject publisher conflicts by default. Explicit `--replace-id` on an initial stable release may transfer ownership from an existing ID to a new ID with the same name, retaining historical VSIX files and a signed catalog backup. Other plugin names, beta replacements and existing destination IDs are rejected. This transfer does not bypass client identity checks. See [publisher-identity-correction.md](publisher-identity-correction.md).

Update checks run automatically after startup and every six hours, but each upgrade requires explicit installation confirmation before any VSIX is downloaded or installed. Closing the prompt or choosing later leaves the installed version intact. VS Code's global automatic-update setting cannot bypass confirmation. The owning extension exposes its own check and log commands, with an application-level preference to disable automatic checks.

Verified compatible updates also replace the workbench's top-left mode menu with a green “更新插件” button. Clicking it confirms installation directly through the same updater; dismissing the system notification does not dismiss this button. Mode switching remains blocked during availability, installation, failure/retry and pending activation, while editing and saving remain available. New panels receive the updater's current state; pending activation restores from profile storage before a network check. Invalid/unavailable metadata alone cannot create a gate. See [workbench-plugin-update.md](workbench-plugin-update.md).

After extension-page reload, retained panels receive a fresh state snapshot when the host attaches or the view resumes. A host actually running the pending version reports current immediately, including offline; an old host stays pending even if the newer VSIX exists on disk. This reconciliation does not force a Webview or document reload. See [update-state-after-reload.md](update-state-after-reload.md).

The self-update client only checks its owning extension, uses the user's automatic-check preference, and preserves metadata revisions and pending installs across restarts. Startup and periodic checks require no enrollment or companion extension. Automatic prompts belong to the focused window; background checks defer until focus returns. Cross-window locks protect state commits and installation, and must not be held while waiting for the user. Confirmation rechecks shared pending state before downloading. It does not reload windows, enable disabled extensions or install unrelated plugins. Remote windows and development extensions are excluded from installation in v1. Installation uses VS Code's command and respects its trust/policy prompts. See [self-update-window-focus.md](self-update-window-focus.md) and [embedded-extension-updates.md](embedded-extension-updates.md); the old catalog remains only for download listings and legacy compatibility.

Deployment and release commands are maintained in the publishing tools README; current implementation and verification are recorded in [embedded-extension-updates.md](embedded-extension-updates.md). Earlier standalone-updater work items retain historical evidence only.
