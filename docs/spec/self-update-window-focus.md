# Self-Update Window Focus

Status: Verifying
Date: 2026-11-26
Scope: 修复多 VS Code 窗口中后台通知占住锁，当前窗口看不到更新提示的问题。

## 1. Root Cause and Evidence

用户已安装 0.1.3，等三分钟仍无提示。读取本机日志确认同一 Profile 有多个正常 VS Code 窗口：window1 在 15:48:36 获取 self-update.lock，owner PID 35716 持续存活，state 已记录 revision 12 而没有 pendingVersion；window2 在 15:48:50、15:49:49 均因“另一个窗口正在检查或安装更新”失败。

原实现把 showInformationMessage 的等待放在跨窗口锁内，且后台检查不区分窗口焦点。computer-use 的真实 UI 无障碍树进一步确认：另一项目窗口存在“原型工作台 有新版本：0.1.3 → 0.1.4。”及“安装更新 / 稍后”。未被用户处理的后台通知可以无限持锁，阻止当前窗口检查。服务器可用、签名已验证、扩展正常激活，排除版本、网络和未激活。

## 2. Proposed Behavior

- 自动检查仅在当前窗口有焦点时提示。启动或定时检查发生在后台时，延后到该窗口获得焦点；元信息请求期间失去焦点，也应延后展示。
- 跨窗口锁只覆盖短状态提交和真实安装，不覆盖网络查询和用户等待提示。其他窗口的未关闭提示不能阻塞当前窗口。
- 在用户确认后重新加锁并读取 pending/revision，两个窗口的旧提示都点击安装也只下载/安装一次。保持签名、身份、版本/引擎检查及禁止主动重载。
- 窗口在提示未处理时失焦，回到前台后可以重新显示提示；使用通知标识防止旧通知的回调清理新的提示状态。手动检查仍可显式触发。
- 日志记录焦点延后、发现版本和提示动作，避免无结果的静默跳过难以诊断。

## 3. Verification

- 回归测试应模拟真实 window.state/onDidChangeWindowState：后台启动不展示，切回前台自动检查，取元信息期间切到后台不展示。
- 模拟两个窗口和未完成的通知 Promise，断言等待用户时不持锁；另一个前台窗口能提示，两个确认回调只产生一次安装。
- 真实窗口验收应观察当前前台窗口收到更新提示；保留用户工作区和已安装文件，不删除活动进程的锁，不以抢占活锁掩盖问题。
- 发布修复测试起点 0.1.5 和稳定升级目标 0.1.6，不覆盖已发布版本。继续使用 /vscode-gameflow/metadata.json。

## 4. Rollback and Limits

旧 0.1.3/0.1.4 仍可能在其他窗口持有旧提示。用户关闭该提示或重启相应窗口后锁才会正常释放；不能强删活锁。新实现继续使用相同锁名协调安装。若用户仍运行旧窗口，应明确区分修复代码与旧宿主，避免把新版文件安装成功误当作所有旧宿主已重启。
