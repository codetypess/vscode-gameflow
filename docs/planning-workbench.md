# GameFlow 策划原型工作台：产品方案草案

日期：2026-11-12

状态：流程与交互验证，尚未实现 VS Code 扩展或接入真实 Agent。

## 已确认的方向

- 面向游戏策划，入口位于 VS Code 扩展内。
- AI Agent 分析策划需求，生成 UI 示意与层级结构。
- 策划能够手动调整 AI 结果，也能从空白页面开始。
- 同一策划文档要求的所有界面放在同一张无限画布，每个界面是一组，可以自由拖动；双击进入页面内部编辑。
- 素材生成属于下游环节。本阶段先明确页面结构、控件、交互和验收条件。

用户提供的截图是原型编辑器的参考：页面列表、元件库、画布和控件编辑。以下未被明确确认的范围均为建议，不视为已确定的业务规则。

## 产品目标

让策划把自然语言需求变成可编辑、可追溯、可交给美术和开发的 UI 原型。

必须同时表达三种结构：

1. 页面关系：页面、弹窗、入口、跳转、返回、打开与关闭。
2. 控件层级：容器与子控件、列表与条目、遮挡顺序。父子关系与绘制顺序分别保存。
3. 视觉布局：控件位置、大小、文案、布局约束与状态表现。

无限画布、页面关系、层级树和页面内部编辑共享同一份文档数据。修改名称不应改变节点身份；调整父级不应误写页面导航关系。页面在无限画布上的位置与其内部控件坐标分别保存。

## 策划工作流程

### 1. 输入与分析需求

输入优先支持直接粘贴文本和引用项目内 Markdown。PDF、Word、图片识别可后续接入，避免第一版过早承担文档解析范围。

Agent 提取：

- 页面、弹窗和复用组件。
- 用户操作、显示信息、动态数据与条件。
- 正常、空、加载、失败、不可用等必要状态。
- 进入、退出、返回和取消路径。
- 明确需求、推断建议、缺失信息及冲突。

每个分析条目保留需求来源。不得把 Agent 推断静默转为业务事实。只针对影响结构的缺失信息提出少量问题；未阻塞布局的问题保留为待确认项。

### 2. 审阅结构方案

先审页面清单、导航关系和组件树，再确认线框。策划可以修改、删除、补充或接受单项建议。

确认并非每一步都弹窗；一般编辑立即生效。Agent 批量变更以候选方案呈现，支持逐项接受或整批采用。

### 3. 编辑原型

- 左侧：全部页面与弹窗；进入页面后显示其控件层级和元件库。
- 中央：同一张无限画布同时容纳全部界面；页面关系可作为连线叠加显示。
- 总览：单击选择页面组，拖动移动整页；空白拖动画布，滚轮缩放，支持适配全部界面。
- 页面编辑：双击页面进入内部编辑范围；相机聚焦该页，其他页面作为上下文减淡显示。返回总览或 Escape 恢复先前视角。
- 右侧：总览时为页面组属性；进入编辑后为控件属性、交互、来源与 Agent 建议。
- 需求分析视图：原始需求、结构化分析与待确认项。

线框使用真实结构节点：文本、按钮、图片占位、容器、列表、输入框、页签、弹窗。一个生成结果应能立即继续手动编辑。

建议支持选择、拖动、调整尺寸、重命名、修改父级、排序、复制、删除、撤销与重做。明确区分节点名称、显示文案和业务标识。

页面组移动不改变内部控件位置；内部控件编辑不改变页面组在世界画布中的位置。平移与缩放属于视图操作，不占用内容撤销步。一次拖动作为一个可撤销事务。

画布底部居中放置浮动工具条：选择、平移、评论、绘制与 AI 入口。绘制菜单向上展开；原型先支持文字、矩形和椭圆。总览绘制作为画布标注，页面编辑内绘制作为当前页控件；评论保留独立批注语义。创建后回到选择，快捷键在输入框内不生效。AI 入口区分可查看的需求分析示例与尚未接入的图像生成。

### 4. 用 Agent 迭代选定范围

例如：“将道具详情改成底部弹窗，保留现有按钮文案”。

发送当前选区、相关需求、已确认决策和必要上下文。返回有范围的修改建议，明确新增、修改和删除。默认保护策划手动修改的内容；有冲突时要求选择具体结果。

需求更新后标记受影响的节点，不自动重建整个页面。

### 5. 评审与交付

保存项目内的结构化文件，并输出可读规格说明和原型图。交付至少包含：页面清单、组件层级、文案、交互、状态、需求来源和未决问题。

只有策划确认后，才把选定页面或组件送入下游美术流程。下游返回的图片应绑定原节点，不以图片内容覆盖业务结构。

## 第一版建议范围

| 能力 | 第一版验收条件 |
| --- | --- |
| 需求分析 | 原始需求能对应到结构条目；推断和待确认项可辨认 |
| AI 草案 | 生成页面、弹窗、控件树和低保真线框；输出通过结构校验 |
| 无限画布 | 全部界面同时摆放；页面组自由拖动；平移、缩放与适配全部 |
| 编辑范围 | 双击进入页面编辑，退出恢复总览视角；控件修改同步回页面组 |
| 手动编辑 | 改文案、移动、改尺寸、增删控件、改父级；树和画布同步 |
| 交互描述 | 支持打开页面、打开/关闭弹窗、返回与简单状态切换 |
| AI 局部修改 | 可查看差异；保留受保护节点；可撤销 |
| 项目保存 | 关闭并重开 VS Code 后，结构与布局仍一致 |
| 输出 | 保存结构化文档、导出规格 Markdown 和原型图 |

复杂动画时间线、完整运行时逻辑、高保真美术、多人与云端同步、直接生成 LayaAir 场景建议后续迭代。这里是范围建议，不是对最终产品范围的限制。

## VS Code 内的实现建议

推荐用 Custom Editor 承载原型文档，以 Webview 显示画布、关系图和属性面板。活动栏 TreeView 提供项目级入口。Chat Participant 可以作为后续补充，不替代主编辑器。

文档建议使用 `.gameflow.json`，文档层独立于 Webview，便于版本管理、外部 Agent 读取和后续引擎转换。

示意模型：

```text
Project
  schemaVersion
  documentId
  revision
  requirements[]   原始条目、来源、明确/推断/待确认
  decisions[]      策划确认及其依据
  pages[]          页面或弹窗、世界画布位置、尺寸、根节点
    nodes[]        稳定 ID、父级、顺序、类型、文案、布局、来源
    states[]       正常、空、禁用等状态差异
  interactions[]   触发节点、事件、条件、动作和目标
  assets[]         后续绑定的图片、皮肤等资源
EditorViewState
  camera           平移位置与缩放比例
  editingScope     总览或指定页面
  overviewCamera   进入页面前的总览视角
```

生成与手动操作最终都转换为同一种文档编辑事务。原型不应有独立的“AI 版结构”和“手动版结构”。

### Agent 集成边界

由扩展宿主管理 Agent 调用和凭据。Webview 不持有模型密钥，也不直接调用供应商。

先定义供应商无关接口：

```text
analyzeRequirements(input, context) -> analysis + openQuestions
proposePrototype(analysis, decisions) -> candidateDocument
proposeChanges(documentRevision, selection, instruction) -> changeProposal
```

每份变更建议必须包含基准版本、操作列表、影响范围和说明。应用前检查：节点 ID、父级合法性、循环引用、跨页面引用、目标存在性、属性范围、保护状态以及基准版本是否过期。

Agent 生成期间策划仍可编辑；如果版本已变化，保留候选结果并进行冲突审阅，不覆盖新编辑。失败、取消和重试不应导致文档部分写入。

模型输出作为数据处理，不执行任意代码。参考文档里的命令和操作说明不自动成为 Agent 执行指令。

### 数据与编辑一致性

- 使用稳定 ID，重命名不改变引用。
- 明确坐标是否相对父级；修改父级时定义保留视觉位置还是采用新布局。
- 撤销覆盖一次完整编辑事务，包括关联引用的变化。
- 删除被引用节点时显示影响，或一并修复相关交互。
- 原型文件保存、未保存提示和文件版本冲突遵循 VS Code 行为。
- 主题使用 VS Code 主题变量；Webview 采用受限资源策略。

## 交互概念原型的范围

本次随对话展示的原型采用内置背包案例，演示：

- 需求分析与无限画布，画布内同时显示三个页面/弹窗。
- 页面组选择、自由移动、画布平移/缩放、适配全部及关系连线。
- 双击进入页面内部编辑，返回总览恢复视角；控件树与画布联动。
- 拖动、文案/类型/位置/尺寸/父级调整、添加与删除。
- 撤销、重做以及手动编辑后的 AI 覆盖保护。
- 单项 Agent 示例建议的采用与保护冲突。

该原型不调用真实 Agent、不读写项目原型文件、不模拟真实业务数据，也不代表 VS Code 扩展已经实现。需求文本可以编辑，但分析结果是固定示例。

## 后续需要落实的选择

1. 团队实际使用哪种 Agent 或模型接入方式，以及账号权限与成本来源。
2. 是否需要支持导入现有原型工具的数据；用户截图当前仅作交互参考。
3. 第一版主要面向横屏、竖屏还是两者；默认布局采用绝对定位还是容器约束。
4. 交付优先级：策划评审、开发规格，或进一步转换为 LayaAir 场景。

建议先用一个真实的“背包 → 道具详情 → 使用反馈”需求贯穿验证，再确定扩展实现范围。衡量结果应包括需求遗漏、人工修改成本与结构可交付性。
